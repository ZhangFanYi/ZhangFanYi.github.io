## 概述

具身智能模型的适配与优化是我司我部门今年6月以来需求明显增长的新业务 部门安排我和另外两名同事长期关注并完成相关工作 与此同时 也和训练组的同事互通有无 讨论具身智能模型的适配与优化思路

### 一、适配
适配的方案是统一的 拉取官方代码仓后 删除toml文件中nv相关的包库以及所有海光适配的包 然后在海光的基础镜像的基础上一键安装 最后补全海光版本的包即可 根据开箱测试中遇到的报错进行代码仓的修改或包版本的调整即可

### 二、优化
具身智能模型的优化有两个大方向 既有**宏观** 又有**微观**方法这两面特点体现了具身智能模型本身的特点

### 宏观
根据trace文件看耗时占比高的算子 gemm或者miopen占比高就去对应的调优 其次就是看空泡水平和是否overlap 空泡通常可以通过三种方法解决 a:pp设置的比较大 b:或者数据读取的太慢 可以增加dataloader的线程数 或者开启prefetch c:增加bs提高卡的利用率 overlap可以通过修改训练过程中的行为来实现 或者显式开启 另外具身智能出现的“常客”卷积带来的2d或者3d算子的布局优化问题是该领域默认的一项优化 需要分析再一次完整的训练迭代中 算子的layout和变化来针对性的做channel last

### 微观
训练过程中的行为涉及到微观方法 需要分析的点有三 模型结构 输入类型 训练框架 这些共同决定了训练性能的上限 根据模型结构和输入类型可以决定是否能够做融合以及做融合的方式  训练框架和实现决定了模型在训练中的各类计算如注意力的实现 梯度 优化器的状态和行为 这又涉及到通信 训练框架又和显存息息相关 不仅决定切分对象和并行方式  还决定了随之而来的通信 能否在训练中减少重复通信 消除重复缓存  修改通信桶的大小等实现优化 是分析的重点 

当然在具体模型中 遇到的各种各样的问题 比如融合时触发的重编译导致性能劣化或者报错 需要具体分析输入的状态 首先要分析原生的dynamo和guard的行为 然后根据实际输入和配置修改 比如在cosmos中 就在开启融合时对发、的max_seqlen进行分桶规避重编译 同事在guard中加入is.compiling判断 在不开启融合时仍然按照精确长度计算 在lingbot-va中 开启融合会导致性能劣化 因为block中包裹了本就优化过的flexattention 因此只能将若干热点算子单独提出并融合 并且加入dynamic=True来修改Dynamo的特化策略 分别避免了python值和shape抖动源 实现避免recompile+性能提升

可以修改fa的参数（cosmos）或者修改融合的粒度和对象（lingbot-va） 

Ps：在具身场景中 如果为了实现某种优化不得不开启offload 这其中显存和内存的读写和优化的收益孰轻孰重需要评估
